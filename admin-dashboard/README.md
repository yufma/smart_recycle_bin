# 리루프 · 스마트 분리수거 관리 MVP

대회 시연을 위한 관리자 웹 애플리케이션입니다. 실물 쓰레기통 1대의 센서 연결과 3층 더미 건물의 수거 경로를 함께 보여 줍니다.

## 2026-10-31 수정 사항

| 문제 | 수정 후 동작 |
| --- | --- |
| 전송 도구에 칸 정보가 없어 HTTP 422 발생 | `--compartment`를 필수로 받아 새 센서 API와 같은 형식으로 전송 |
| 다른 칸의 새 측정이 오래된 값을 현재값으로 취급하게 함 | 칸별 시각으로 만료 판단. 화면·경로·수거량·수거 확인은 유효한 칸만 사용하고 이전 기록은 보관 |
| 한 위치의 수거량이 운반 용량을 넘는데 경로가 생성됨 | 대상과 초과량을 표시하고 전체 배정을 중단. 조건을 조정한 뒤 재계산하면 정상 배정 |

이전 버전에서 저장한 경로는 한 번 다시 계산해야 합니다. 용량 초과 결과는 API에서 `blocked_reason: "capacity"`, `capacity_issues`, 빈 `routes`로 구분되며 관리자 부족과 다른 안내를 표시합니다. 한 위치의 자동 분할 운반은 이번 MVP 범위에 포함하지 않습니다.

검증: 자동 테스트 **45개 통과**, `npm run build` 성공. 테스트에는 전송 도구→API 연동, 칸별 만료와 경로 재계산, 기존 시각의 호환 처리, 두 배정 방식의 용량 초과 차단과 복구가 포함됩니다.

## 시작하기

1. `실행하기.cmd`를 더블 클릭합니다.
2. 브라우저에서 `http://127.0.0.1:8765`가 열립니다.
3. **시연 계정으로 둘러보기**를 누릅니다.

시연 계정은 `demo@reloop.local` / `Demo1234!`입니다. 회원가입으로 만든 계정은 각각 독립된 건물 데이터를 갖습니다. 실제 이메일 전송이나 외부 인증 서비스는 사용하지 않습니다.

- 실행 환경: Windows, Python 3.10 이상. GitHub에서 처음 받은 소스를 실행하거나 화면을 다시 빌드하려면 Node.js 20.19 이상이 필요합니다.
- GitHub 저장소에는 소스 코드가 포함됩니다. 첫 실행 시 `dist/`가 없으면 실행기가 화면을 자동으로 빌드합니다.
- 배포 ZIP에 포함된 `dist/`를 사용하는 일반 실행에는 Node.js가 필요하지 않습니다.
- 첫 실행 시 Python 의존성이 없다면 `.venv/`에 설치합니다. 설치가 끝난 뒤에는 인터넷 연결 없이 사용할 수 있습니다.
- 서버는 숨겨진 창으로 실행되며, 브라우저를 닫아도 계속 동작합니다.
- 종료하려면 `종료하기.cmd`를 실행합니다. 데이터는 유지됩니다.
- 시작 오류는 `logs/server.err.log`에서 확인합니다.

PowerShell에서 실행할 수도 있습니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
```

GitHub에서 내려받은 경우 압축을 먼저 풀거나 저장소를 복제한 뒤 프로젝트 폴더의 `실행하기.cmd`를 실행하세요. 최초 의존성 설치에는 인터넷 연결이 필요합니다. 계정·센서값·도면·수거 기록은 저장소에 포함하지 않으며, 실행한 PC의 `data/`에 새로 만들어집니다.

## 기본 구성

| 항목 | 내용 |
| --- | --- |
| 건물 | 3개 층, 층마다 쓰레기통 4개 |
| 칸 | 위치마다 캔 · PET · 유리 · 일반 4칸. 칸마다 적재율이 따로 있고, 위치의 상태는 가장 찬 칸 기준 |
| 실물 | B-001. 연결 전에는 4칸 모두 비워 두고 수신 대기로 표시 |
| 더미 | B-002~B-012. 카드 상세에서 칸별 적재율 조절 가능 |
| 관리자 | 전체 3명, 수거 가능 2명으로 시작. 0~전체 인원으로 조절 |
| 관리자실 | 1층(F1-OF1). 관리자 경로의 출발 지점 |
| 분리수거장 | 1층 복도 동쪽(F1-DP1). 경로가 여기서 비우고 끝남 |
| 정상 | 80% 미만, 초록 |
| 주의 | 80% 이상~90% 미만, 주황 |
| 수거 필요 | 90% 이상, 빨강 |
| 기본 경로 | 빨강만 포함. ‘주황색 쓰레기통도 포함’ 선택 가능 |
| 새로고침 | 5초 간격. 화면이 백그라운드이면 일시 중지 |

상태 기준은 설정에서 변경할 수 있습니다. 실물 센서의 측정 시각은 **칸마다 따로** 확인합니다. 수신 지연 기준(기본 5분)을 넘긴 칸은 ‘수신 대기’로 표시하고 현재 적재율·수거 대상·운반량·수거 시간 계산에서 제외합니다. 다른 칸의 새 측정은 해당 칸의 유효 시간을 갱신하지 않습니다.

일부 칸만 최신 값이 있으면 ‘일부 칸 수신 대기 · 최신 값만 반영’을 표시합니다. 모든 칸의 값이 없거나 오래되면 쓰레기통 전체가 수신 대기가 됩니다. 이전 측정값과 시각은 로컬 기록·백업에 보관하며, 상세 화면에서는 ‘이전 기록(계산에서 제외)’로 구분합니다. 칸 값이 만료되어 수거량이 달라지면 기존 경로에도 재계산 안내가 표시됩니다.

## 권장 시연 순서

1. 시연 계정으로 로그인합니다. 층별 쓰레기통 번호와 적재율을 설명합니다.
2. **수거 경로 계산**을 누릅니다. 빨간 쓰레기통 3개가 배정되는 것을 확인합니다.
3. **주황색 쓰레기통도 포함**을 선택합니다. 수거 대상이 6개로 늘어납니다.
4. 동일한 상태에서 수거 가능 인원을 1명, 2명, 3명으로 바꿉니다. 관리자별 담당 목록과 예상 완료 시간이 바뀝니다.
5. 지도에서 1F·2F·3F를 전환하고 관리자별 경로를 선택합니다. 지도 안의 작은 숫자는 해당 관리자의 방문 순서입니다.
6. **장치 연동**에서 실제 센서값을 받거나, ‘실물 위치 시뮬레이션’을 96%로 적용합니다. 시뮬레이션은 실제 센서와 별도로 표시됩니다.
7. 경로를 다시 계산합니다. 입력 상태가 변경된 기존 경로에는 재계산 안내가 표시됩니다.
8. 담당 쓰레기통의 **수거 완료**를 누릅니다. 남은 경로가 갱신되고 **수거 기록**에 저장됩니다.

‘시연 시나리오’에는 일반적인 하루, 점심시간 이후, 수거를 마친 건물이 있습니다. 시나리오는 더미 쓰레기통만 변경합니다.

다음 시연 전에는 설정의 **대회 시연 초기화**에서 **기본 건물로 초기화** 또는 **큰 건물 예시로 바꾸기**를 선택할 수 있습니다. 현재 계정의 배치와 수거 기록이 초기화되므로, 보관할 데이터는 먼저 백업하세요.

곡선형 건물 예시는 양 끝이 반원인 운동장 트랙 모양의 4층 컨벤션센터로, 쓰레기통 61개, 관리자 8명(수거 가능 5명)입니다.
- 바깥·안쪽 곡선 복도 두 겹을 방사형 통로 8개가 잇고, 가운데는 중앙 홀(2층부터는 보이드)입니다.
- 양 끝에 계단 2곳, 북·남쪽에 엘리베이터 2대가 있습니다. 관리자실은 1층 운영사무실과 3층 기술지원실, 분리수거장은 1층 하역장입니다.
- 지도는 0~100 좌표를 가로 900·세로 460 화면에 늘려 그리기 때문에, 이 건물은 곡선이 화면에서 둥글게 보이도록 화면 픽셀 기준으로 배치했습니다. 곡선 복도의 연결에는 그 모양에서 잰 실제 거리(m)가 들어 있습니다.
- 배치는 `server/sample_layout.py`의 `ROUND_*`, 도면은 `python tools\make_round_floorplans.py`로 다시 그립니다.

복합청사 예시는 8층 A동(행정동)과 5층 B동(문화복지동)을 중앙 연결동이 잇는 건물로, 쓰레기통 79개, 관리자 8명(수거 가능 5명)입니다.
- 두 동은 각각 복도가 고리 모양으로 돌고, 6~8층에는 A동과 연결동만 있습니다.
- 층간 이동은 A동 서쪽 계단, 중앙 계단, 중앙 엘리베이터(1~8층)와 B동 동쪽 계단, B동 화물 엘리베이터(1~5층)로 합니다.
- 화물 엘리베이터는 3층에서 운영 중단입니다.
- 관리자실은 1층 종합상황실과 6층 총무과, 분리수거장은 1층 하역장과 주차장 수거함 두 곳입니다.
- 배치는 `server/sample_layout.py`의 `CIVIC_*`, 도면은 `python tools\make_civic_floorplans.py`로 다시 그립니다.
- 지점이 많은 건물을 위해 한 건물의 지점은 400개, 연결은 1,200개까지 저장할 수 있습니다.

도서관 예시는 6층, 쓰레기통 45개, 관리자 6명(수거 가능 4명)입니다. 층마다 가운데 아트리움을 고리 모양 복도가 둘러싸고, 서쪽·동쪽 계단과 아트리움 북·남쪽 엘리베이터 2대가 있습니다. 관리자실은 1층 시설관리실과 4층 사서실 두 곳이고, 분리수거장은 1층 하역장입니다. 배치는 `server/sample_layout.py`의 `LIBRARY_*`, 도면은 `python tools\make_library_floorplans.py`로 다시 그립니다.

큰 건물 예시는 5층, 쓰레기통 30개, 관리자 5명(수거 가능 3명)입니다. 층마다 북쪽·남쪽 복도가 서쪽 계단, 동쪽 계단, 중앙 엘리베이터로 이어지고, 관리자실은 1층 시설 관리실(F1-OF1), 분리수거장은 1층 학생 라운지(F1-DP1)입니다. 방 이름이 있는 층별 도면(`server/samples/large-floor-N.png`)이 함께 등록됩니다. 배치는 `server/sample_layout.py`에 있고, 도면은 `python tools\make_large_floorplans.py`로 다시 그릴 수 있습니다(Pillow와 한글 글꼴 필요).

## 배치 편집

- **건물·배치도**에서 건물 이름과 층수를 저장합니다.
- ‘쓰레기통’ 도구를 선택한 뒤 지도 위를 클릭하면 더미 쓰레기통을 추가합니다.
- ‘지점 설정’ 도구에서 놓을 지점(복도, 관리자실, 분리수거장)을 고른 뒤 지도를 클릭합니다. 관리자실과 분리수거장은 여러 곳 둘 수 있습니다. 이미 있는 지점을 다시 클릭하면 지워집니다.
- 계단·엘리베이터는 ‘지점 설정’ 오른쪽 목록에서 **계단 추가**·**엘리베이터 추가**로 먼저 만들고(ST1, EL1 …), 하나를 고른 채 층마다 지도에 놓습니다. 같은 계단·엘리베이터의 층끼리는 아래층부터 차례로 자동 연결됩니다.
- 그 밖의 연결은 자동으로 만들지 않습니다. 복도·관리자실·분리수거장·계단·엘리베이터 지점은 ‘통로 연결’ 도구로 직접 잇습니다.
- **층간 이동** 표에서 계단·엘리베이터를 지도에 놓은 층의 체크를 끄면 그 층은 운영 중단이 됩니다. 지점과 복도 연결은 남지만 그 층에서는 타고 내릴 수 없고, 위아래 운영 층끼리 바로 이어집니다.
- ‘선택·이동’에서 쓰레기통과 지점을 드래그합니다. 쓰레기통 이동은 바로 저장되고, 지점의 추가·이동·삭제와 연결은 **지점·통로 저장**을 눌러 적용합니다.
- 쓰레기통은 같은 층의 연결 통로를 선택해야 합니다. 이 통로에서 해당 위치로 직접 접근할 수 있도록 배치하세요.
- 층간 이동 시간은 설정의 계단·엘리베이터 시간으로 계산합니다. 층간 연결에 입력한 거리는 걷는 거리 합계에만 쓰입니다.
- 칸이 생기기 전 형식(쓰레기통마다 품목 하나와 적재율 하나)의 작업 공간과 백업은 읽을 때 그 품목의 칸에 원래 적재율을 넣고, 나머지 칸은 0(실물 장치는 값 없음)으로 바뀝니다. 혼합·일반은 일반 칸으로 갑니다.
- 예전 형식(관리자실 1곳을 설정값으로, 분리수거장을 통로 지점 지정으로 저장)의 작업 공간과 백업은 읽을 때 관리자실·분리수거장 지점으로 바뀌고, 예전과 같은 통로에 연결됩니다.
- 도면은 PNG·JPG·WEBP, 최대 4MB입니다. 업로드한 도면의 벽이나 복도를 자동 인식하지 않습니다. 통로는 직접 지정합니다.
- 도면 좌표는 가로·세로 각각 0~100이고, 지도는 이를 가로 900 · 세로 460 화면에 그립니다. 올린 도면은 원래 비율 그대로 이 영역 가운데에 맞춰 보여 줍니다.
- 거리는 화면에 보이는 비율대로 잽니다. 축척(기본 1단위=0.6m)은 가로 1칸 기준이고, 세로 1칸은 그 460/900입니다. 실제 도면은 설정에서 축척을 조정합니다.
- 제거할 층에 쓰레기통이나 지점이 있으면 먼저 다른 층으로 옮기거나 삭제해야 합니다.

## 수거 동선 계산

1. 최신 상태에서 빨강, 또는 빨강+주황 대상을 선별합니다.
2. **이동 시간 그래프**를 만듭니다. 비용은 거리가 아니라 초 단위 시간입니다.
   - 복도: 거리 ÷ 보행 속도
   - 계단: 오르기와 내려가기를 층당 따로 계산합니다(기본 20초, 14초).
   - 엘리베이터: 탈 때마다 기다리는 시간을 한 번 넣고(기본 40초), 층당 이동 시간(기본 4초)을 더합니다. 엘리베이터 지점마다 '승강기 안' 지점을 따로 두기 때문에, 엘리베이터 앞을 지나가기만 할 때는 기다리는 시간이 붙지 않습니다.
   - 수거 카트를 쓰면 계단은 쓰지 않고, 보행 속도를 85%로 계산합니다. 엘리베이터가 없는 층은 수거 대상에서 빠집니다.
   - 기본 시간값은 가정입니다. 현장에서 재서 **설정 → 이동과 수거 조건**에서 맞춥니다.
3. 다익스트라 알고리즘으로 관리자실·분리수거장·대상 사이의 가장 빠른 이동 시간과 경로를 구합니다. 위아래 시간이 달라 방향이 있는 그래프입니다.
4. 관리자별 경로는 첫 대상에 가장 빨리 닿는 관리자실에서 출발해 분리수거장에서 비우고 끝납니다. 분리수거장이 없으면 관리자실에서 비웁니다.
   - 여러 위치를 수거하면서 한 번에 옮길 양(가득 찬 칸 기준 개수)을 넘게 되면 중간에 분리수거장에 들러 비우고 이어서 돕니다.
   - 용량 단위는 **가득 찬 칸 1개 분량**입니다. 한 위치에서 비울 칸들의 합이 용량보다 크면 전체 경로 계산을 중단하고 쓰레기통 번호·필요량·허용량을 표시합니다. 예: 네 칸이 모두 100%이고 용량이 1이면 `B-002: 수거량 4칸 분량 / 운반 가능 1칸 분량`을 안내합니다.
   - MVP는 **한 위치를 여러 번 방문해 나눠 운반하는 기능을 지원하지 않습니다.** 실제 운반 가능한 양과 측정값을 확인한 뒤 다시 계산하세요. 조건에 맞는 다른 위치만 배정해 초과 위치를 숨기거나, 운반 용량을 자동으로 늘리지 않습니다. 여러 위치 사이에서 비우는 기존 기능과 `0 = 용량 제한 없음` 설정은 유지됩니다.
   - 방문 순서가 정해지면, 어디서 끊고 어느 분리수거장으로 비우러 갈지는 동적 계획법으로 가장 빠르게 정합니다.
   - 한 칸이라도 기준을 넘으면 그 위치가 수거 대상이 됩니다. 들르면 주의 기준 이상인 칸을 모두 비웁니다(그런 칸이 없으면 전부). 카트에 싣는 양은 비우는 칸들의 적재율 합(가득 찬 칸 기준)입니다.
   - 예상 시간 = 이동 시간 + 위치마다 (기본 수거 시간 + 비우는 칸 수 × 칸 수거 시간) + 분리수거장에서 비우는 횟수 × 비우는 시간
5. 수거 동선 화면에서 프리셋을 고르면 그 기준으로 관리자에게 배정합니다. 두 프리셋의 끝나는 시간, 인원, 작업 합계를 함께 보여 줍니다.
   - **빨리 끝내기**: 마지막 관리자가 일을 마치는 시각을 가장 앞당기고, 같으면 작업 시간 합계가 작은 쪽을 고릅니다. 한 사람 작업 시간 상한을 지킬 수 있으면 이 방식이 저절로 지키고, 못 지키면 '상한 초과'로 표시합니다.
   - **인력 아끼기**: 한 사람 작업 시간 상한(기본 20분) 안에서 가장 적은 인원을 쓰고, 인원이 같으면 마지막 관리자가 가장 빨리 끝나는 배정을(그것도 같으면 작업 시간 합계가 작은 쪽을) 고릅니다. 상한을 지킬 수 없으면 가장 많이 넘는 사람의 초과 시간부터 줄입니다.
6. 배정은 적응형 대규모 이웃 탐색(ALNS)으로 찾습니다.
   - 첫 답은 먼 대상부터 가장 싼 자리에 끼워 넣어 만듭니다.
   - 그다음 대상 몇 개를 빼고 다시 넣기를 반복합니다. 빼는 규칙은 무작위, 가장 비싼 대상, 서로 가까운 대상 묶음, 한 사람 경로 통째 중에서 고릅니다. 다시 넣을 때는 가장 싼 자리, 또는 후회값(regret-2) 기준을 씁니다. 결과가 나빠져도 담금질 확률로 받아들이고, 효과가 좋은 규칙을 더 자주 고릅니다.
   - 마지막에 관리자 사이 대상 옮기기·맞바꾸기와 경로 안 순서 뒤집기(2-opt)·지점 옮기기로 다듬습니다.
   - 시간 한도(프리셋당 약 0.6초) 안에서 난수 시작값을 바꿔 최대 4번 탐색하고, 가장 좋은 답을 씁니다. 같은 입력이면 같은 결과가 나오도록 난수는 입력값으로 고정합니다.
   - 두 프리셋을 모두 계산한 뒤, 각 프리셋 기준으로 더 나은 쪽 결과를 씁니다. 그래서 '빨리 끝내기'가 '인력 아끼기'보다 늦게 끝나는 일은 없습니다.
   - 대상 6~7개 사례(카트 용량·분리수거장 포함)에서는 모든 배정·방문 순서·비우기 위치를 다 계산한 결과와 같았습니다. 대상이 많은 경우에는 최적값을 보장하지 않습니다.

관리자 0명, 수거 대상 없음, 끊어진 통로, 관리자실과 연결되지 않은 쓰레기통은 각각 별도로 표시합니다. 관리자실이 없거나 통로와 이어지지 않은 관리자실·분리수거장이 있으면 수거 동선 화면에 고칠 곳을 안내합니다. 실제 인력 추적이나 자동 출근 감지는 없으며, 수거 가능 인원은 시연자가 직접 입력합니다.

## 실물 센서 연결

1. **장치 연동 → 장치 연결 키 발급**에서 키를 생성하고 장치 설정에 복사합니다.
2. 센서나 게이트웨이가 아래 요청을 보냅니다.

```http
POST /api/device/readings
Content-Type: application/json
X-Device-Key: 발급한_장치_연결_키
```

```json
{
  "bin_id": "B-001",
  "compartment": "PET",
  "fill_percent": 94
}
```

여러 칸을 한 번에 보낼 수도 있습니다.

```json
{
  "bin_id": "B-001",
  "fills": { "CAN": 40, "PET": 94, "GLASS": 15, "OTHER": 60 }
}
```

칸은 `CAN`(캔), `PET`, `GLASS`(유리), `OTHER`(일반)이고, 적재율은 0~100의 숫자입니다. 칸 없이 `fill_percent`만 보내면 거절합니다. 수거 완료 후에는 비운 칸의 새 측정값이 모두 들어와야 '수거 확인 중'이 풀립니다. 시뮬레이션 값은 실제 측정을 처음 받을 때 지워지고 섞이지 않습니다. `measured_at`에 시간대가 있는 ISO 8601 측정 시각을 추가할 수 있습니다. 예: `2026-10-30T10:30:00+09:00`. 생략하면 서버 수신 시각을 사용합니다. 같은 칸에서 이미 처리한 값보다 오래된 측정은 거절합니다.

연결 키는 발급한 계정의 실물 장치에만 적용됩니다. 키를 다시 발급하면 이전 키는 만료됩니다. 키 원문은 데이터베이스에 저장하지 않습니다.

실물 값을 수신하면 시뮬레이션 표시가 자동으로 실제 센서 표시로 바뀝니다. 실물 장치의 수거 완료는 측정값을 임의로 0으로 만들지 않습니다. 다음 센서 측정으로 실제 비워진 상태를 확인합니다.

센서 전송 테스트용 도구도 제공됩니다.

```powershell
python tools\send_reading.py --compartment PET --fill 94
```

`--compartment`는 필수이며 `CAN`, `PET`, `GLASS`, `OTHER` 중 하나를 지정합니다(소문자도 허용). `--fill`은 0~100의 숫자입니다. 칸을 생략하거나 잘못된 값을 넣으면 키를 묻거나 요청을 보내기 전에 사용법을 안내합니다. 예전 `--fill 94` 명령에는 칸 선택을 추가해야 합니다.

실행 후 연결 키를 입력합니다. 이미 `RELOOP_DEVICE_KEY` 환경 변수가 설정되어 있으면 그 값을 사용합니다. 다른 서버에 전송하려면 `--url http://서버PC의IP:8765`, 다른 실물 번호를 지정하려면 `--bin B-001` 옵션을 사용하세요. 키를 코드나 README에 직접 넣지 않습니다. 이 도구의 테스트 패킷은 실물 수신 경로로 들어가므로 대회 발표에서는 테스트 입력과 실제 센서 측정을 구분해 설명하세요.

센서는 바뀐 칸만 보내는 대신 각 칸의 상태를 수신 지연 기준 안에 주기적으로 전송해야 합니다. 작업 공간 API의 `compartments`·`fill`은 유효한 현재값이고, 만료된 칸은 `null`입니다. `last_compartments`와 `compartment_measured_at`은 마지막 측정 기록, `stale_compartments`는 만료된 칸 목록, `partial_reading`은 일부 칸만 유효한지를 나타냅니다. 단일 시각만 저장하던 이전 데이터는 그 원래 시각으로 칸별 시각을 보완하므로 새로운 측정으로 간주하지 않습니다.

수거 완료와 확인 대기도 유효한 칸만 대상으로 합니다. 오래된 칸은 운반량과 수거 기록의 비운 칸에 포함되지 않으며, 그 칸의 새 측정을 기다리느라 수거 확인이 막히지 않습니다.

다른 기기의 센서를 연결하려면 서버를 종료한 뒤 LAN 모드로 다시 실행합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Lan
```

센서의 전송 주소는 `http://서버PC의IP:8765/api/device/readings`입니다. 기존 서버가 실행 중이면 모드가 바뀌지 않으므로 먼저 `종료하기.cmd`를 실행합니다. 같은 사설 네트워크에서 통신할 수 있어야 합니다. 기본 실행은 이 PC에서만 접속할 수 있습니다.

## 안드로이드 앱

`android/`는 대시보드를 휴대폰 화면에 띄우는 웹뷰 앱입니다. 화면과 데이터는 PC 서버에 그대로 있고, 앱은 서버 주소를 열기만 합니다.

- 빌드: `.\android\build-apk.ps1` (네트워크 없이 로컬 Gradle 9.6.0 · Android Gradle Plugin 9.4.0 캐시 사용). 결과는 `android\dist\reloop-admin.apk`이고, 시험용으로 디버그 키로 서명합니다.
- 설치: 휴대폰의 USB 디버깅을 켜고 `adb install -r android\dist\reloop-admin.apk`. 설치할 때 휴대폰에 Play 프로텍트 확인 창이 뜨면 휴대폰에서 직접 승인합니다.
- 연결: 기본 주소는 `http://127.0.0.1:8765`입니다. USB로 연결한 뒤 PC에서 `adb reverse tcp:8765 tcp:8765`를 실행하면, 휴대폰의 이 주소가 PC 서버로 이어집니다. adb를 다시 시작하거나 케이블을 다시 꽂으면 이 명령을 다시 실행합니다.
- 서버에 연결할 수 없으면 앱에 '서버 연결' 화면이 나오고, 여기서 주소를 바꿀 수 있습니다. 같은 네트워크의 PC IP를 쓰려면 서버를 LAN 모드로 실행해야 합니다.
- 도면 업로드와 백업 복원은 휴대폰의 파일 선택 창을 씁니다. 백업 다운로드는 휴대폰의 다운로드 폴더에 저장합니다. 수거 기록 CSV는 화면 안에서 만드는 파일이라 앱에서는 내려받을 수 없으니 PC 브라우저를 씁니다.
- 뒤로 가기 버튼은 대시보드 안에서 이전 화면으로 돌아가고, 더 갈 곳이 없으면 앱을 닫습니다.

## 저장 및 백업

- 데이터베이스: `data/reloop.sqlite3`
- 업로드 도면: `data/maps/`
- 저장 내용: 계정, 건물 설정, 위치, 통로, 적재율, 수거 기록, 최근 수신 기록, 마지막 경로
- 계정 비밀번호: 무작위 소금값과 PBKDF2-SHA256으로 저장
- 로그인 세션: HttpOnly·SameSite 쿠키, 만료 7일
- 계정마다 워크스페이스가 분리됩니다.
- 설정의 백업 다운로드는 건물·도면·운영 기록을 내보냅니다. 비밀번호·세션·장치 키는 제외됩니다.
- 복원 후 실물 장치는 새로운 측정을 기다립니다. 백업의 과거 실물값을 현재값으로 사용하지 않습니다.

이 앱은 대회용 로컬 MVP입니다. 실물 장치의 펌웨어·게이트웨이는 위 전송 형식에 맞춰 별도로 연결해야 합니다. 서버 수신 기능과 모의 패킷 동작은 검증할 수 있지만, 실제 센서의 정확도나 무선 연결 품질은 해당 장치로 현장 확인이 필요합니다.

## 개발 및 검증

```powershell
npm ci
npm run build
python -m pytest tests -q
```

개발 중에는 `python -m uvicorn server.app:app --host 127.0.0.1 --port 8765`와 `npm run dev`를 별도 터미널에서 실행합니다. Vite 화면 주소는 `http://127.0.0.1:5173`이며 API는 로컬 서버로 전달됩니다. 일반 시연에서는 미리 빌드된 화면과 API를 8765 포트 하나로 제공합니다.

구성: React + TypeScript + Vite / FastAPI / SQLite. 외부 로그인, 지도 서비스, 클라우드 저장, 외부 폰트에 의존하지 않습니다.
